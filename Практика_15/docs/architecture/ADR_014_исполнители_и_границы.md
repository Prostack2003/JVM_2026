# ADR 014: исполнители и границы владения

## Статус

Принято 3 октября 2026 года.

## Контекст

Дневник может независимо анализировать много планов. При этом SQLite, JavaFX-узлы и общие изменяемые счётчики не должны случайно стать общей памятью для всех задач.

## Решение

- читать репозиторий до границы параллелизма;
- передавать задачам только `List.copyOf` неизменяемых `NutritionPlan`;
- создавать один виртуальный поток на независимую диагностику;
- собирать итоги только после ожидания всех `Future`;
- для одиночных общих счётчиков использовать `AtomicInteger`;
- закрывать каждый `ExecutorService` в `try`-with-resources;
- при ошибке отменять остальные `Future`, но не подменять исходную причину.

## Отклонённые варианты

- Один общий JDBC `Connection` во всех задачах: нет явной модели владения и лимита дефицитного ресурса.
- `volatile int`: даёт видимость, но не делает read-modify-write атомарным.
- Публикация частичного пакета: получатель не может отличить завершённую диагностику от ещё работающей.
- Неограниченное `Future.get()`: зависшая задача удерживает весь сценарий.

## Последствия

Код диагностики не зависит от JavaFX и JDBC, его можно детерминированно проверять. Появляется явная стоимость: снимок занимает память, а ожидающий поток должен иметь таймаут и политику отмены.
