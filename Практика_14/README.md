# Практика 14. Исполнители, виртуальные потоки и гонки данных

Самостоятельный Gradle-проект дневника питания КБЖУ. Проект детерминированно показывает потерю обновления, исправляет её с `AtomicInteger`, ожидает все `Future` виртуальных потоков и корректно закрывает исполнители.

## Требования

- JDK 25 (проверено на 25.0.4);
- Linux, macOS или Windows;
- графическая среда только для запуска наследуемого JavaFX-окна;
- Интернет только при первой загрузке Gradle 9.1, JavaFX 25 и SQLite JDBC.

## Сборка и приёмка

Из каталога `Практика_14`:

```shell
./gradlew clean check testConcurrency runLessonDemo
```

Windows:

```text
gradlew.bat clean check testConcurrency runLessonDemo
```

`runLessonDemo` — основной маршрут приёмки. Точка входа: `ru.npi.kbju.lesson.ConcurrencyDemo`. Он проверяет:

1. два неатомарных read-modify-write после барьера дают `1`;
2. те же два задания через `AtomicInteger` дают `2`;
3. результаты всех диагностик получены в порядке исходного снимка;
4. исходная ошибка из `Future` сохранена как `cause`;
5. ожидающая задача получает interrupt, а её executor завершается без оставшихся задач.

Повтор без сети:

```shell
./gradlew --offline clean check testConcurrency runLessonDemo
```

## Граница параллелизма

`ParallelNutritionDiagnostics` получает `List.copyOf(...)` уже загруженных планов. Виртуальные потоки не получают `NutritionPlanRepository`, `Connection` и JavaFX-узлы. Одно JDBC-соединение нельзя неявно делить между задачами: для этого нужна отдельная модель владения, пул с лимитом или последовательный доступ.

Виртуальные потоки удешевляют блокирующее ожидание, но не делают `count++` атомарным и не ускоряют автоматически CPU-задачи.

## Наследуемое окно

Практика остаётся самостоятельным приложением и сохраняет функции практик 1–13:

```shell
./gradlew run
./gradlew run --args="--smoke"
```

Данные хранятся в `Практика_14/.lesson-data/nutrition-plans.db`; каталог исключён из Git.
