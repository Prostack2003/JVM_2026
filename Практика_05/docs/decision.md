# Объяснение решения и границы этапа

## Сквозной сценарий

При запуске пользователь видит один исходный план питания. Он вводит название нового плана и нажимает кнопку. Обработчик читает поле, передаёт значение `NutritionPlanService`, добавляет возвращённую запись в наблюдаемый список таблицы и показывает результат.

Обработчик не создаёт предметную запись в обход сервиса и не повторяет инварианты `NutritionPlan`. Пустой или пробельный текст отклоняет предметная модель. Интерфейс перехватывает ожидаемую ошибку, сохраняет число строк и объясняет пользователю, что нужно исправить.

## Почему записи исчезают после закрытия

`NutritionPlanService` хранит планы в обычном списке внутри процесса JVM. Новый запуск создаёт новый сервис и одну исходную запись. База данных, файл и сетевое хранилище на этом этапе отсутствуют, поэтому введённые значения намеренно не переживают завершение процесса.

## Альтернатива

Можно было изменять `ObservableList` непосредственно в обработчике кнопки. Такой вариант короче, но смешивает создание предметного объекта и отображение результата. Небольшой сервис оставляет модели обычные Java-типы и готовит понятную границу для следующих этапов без преждевременного добавления базы данных.

## Ограничения

- данные живут только до закрытия приложения;
- экран содержит один основной сценарий;
- FXML и CSS появятся на следующем этапе курса;
- база данных, HTTP и существующий backend не используются.
