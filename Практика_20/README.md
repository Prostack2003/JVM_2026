# Практика 20. Резервная копия и безопасное восстановление

Самостоятельный Gradle-проект дневника питания КБЖУ. Практика создаёт согласованный снимок живой SQLite-базы командой `VACUUM INTO`, повторно открывает копию, проверяет `PRAGMA integrity_check` и версию схемы. Восстановление допускается только в новый тестовый файл и подтверждается сравнением всех предметных записей.

## Требования

- JDK 25 (проверено на 25.0.4);
- Gradle Wrapper 9.1;
- графический сеанс для JavaFX-регрессии;
- Интернет нужен только при первоначальном заполнении кэша Gradle.

## Основная проверка

Из каталога `Практика_20`:

```shell
./gradlew clean testBackupRecovery runLessonDemo
```

Windows:

```text
gradlew.bat clean testBackupRecovery runLessonDemo
```

`testBackupRecovery` проверяет снимок открытой базы, отдельное чтение копии, изменение после снимка, восстановление в новый путь, повреждённый файл, занятую цель, повторный путь копии, несовместимую схему и апостроф в имени каталога.

Полная регрессия самостоятельного проекта:

```shell
./gradlew clean check testBackupRecovery runLessonDemo
```

## Механизм снимка

`SqliteBackupService.create` сначала открывает исходную базу отдельно и проверяет её структуру. Снимок создаётся механизмом SQLite во временный файл в каталоге назначения. Сервис повторно открывает временный файл, требует единственный результат `ok` от `PRAGMA integrity_check`, версию схемы 2 и доступную таблицу `nutrition_plan`. Только после этого файл получает заданное имя.

Существующая копия не перезаписывается. Для нового снимка нужно выбрать новый путь. Обычное файловое копирование открытой SQLite-базы не используется, поскольку рядом с основным файлом могут существовать журнальные файлы.

## Безопасное восстановление

`restoreToNewDatabase` принимает только существующую проверенную копию и новый целевой путь. Сервис отказывается:

- восстанавливать файл поверх него самого;
- заменять рабочую или любую другую существующую базу;
- принимать повреждённый SQLite-файл;
- принимать неизвестную версию схемы.

Копия сначала переносится во временный файл рядом с целью, повторно проверяется и только затем публикуется. Демонстрация открывает восстановленную базу через обычный репозиторий и сравнивает полный список планов со состоянием на момент снимка.

## Воспроизводимый сценарий

```shell
./gradlew runLessonDemo
```

Демонстрация использует новый каталог внутри `/tmp`, а не `.lesson-data` пользователя. Она:

1. создаёт два учебных плана и согласованный снимок;
2. добавляет третий план после снимка и показывает, что старая копия его не содержит;
3. восстанавливает копию в новый файл и сравнивает записи;
4. отклоняет повреждённый файл и сверяет SHA-256 рабочей базы и хорошего снимка.

## Периодичность и RPO

Для дневника КБЖУ принята учебная политика: снимок после закрытия соединений не реже одного раза в сутки и дополнительно перед миграцией либо массовым импортом. Хранятся семь последних суточных копий, причём удаление старых файлов в этой практике не автоматизировано. Заявленный RPO — до 24 часов: изменения после последнего успешного снимка могут быть потеряны.

## Запуск приложения

```shell
./gradlew run
./gradlew run --args="--smoke"
```

Практика не добавляет опасную кнопку замены рабочей базы. Пользовательская интеграция обслуживания должна сначала закрыть `ApplicationContext`, выбрать новый тестовый путь, показать результат проверки и только отдельным подтверждённым процессом решать вопрос о рабочем файле.
