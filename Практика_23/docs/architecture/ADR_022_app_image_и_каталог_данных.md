# ADR 022: app-image и внешний каталог данных

- Статус: принято.
- Дата: 4 октября 2026 года.

## Контекст

Обычный JAR требует правильно установленной Java и ручного classpath. Настольное приложение использует JavaFX, FXML, SQLite JDBC и другие зависимости. Пользовательские данные должны переживать замену исполняемой поставки.

## Решение

Для каждой целевой ОС создаётся собственный `jpackage --type app-image`. В образ входят нативный launcher, все JAR и сокращённый runtime Java. Исходной структурой служит `installDist`; `jdeps` используется для анализа, а окончательный набор модулей подтверждается реальным запуском.

SQLite, журнал и резервные копии размещаются вне app-image: по умолчанию в `~/.kbju-diary`, в приёмке — под явным `--data-dir`. Структурная проверка запрещает `.db` и `.log` внутри образа.

Приёмка копирует образ в каталог без исходников и дважды запускает launcher. Первый процесс добавляет запись через JavaFX-форму, второй подтверждает сохранение. Путь `java.home` обязан указывать на runtime этой копии.

## Последствия

- конечному пользователю не нужен системный JDK;
- поставка больше обычного JAR, но воспроизводима одной Gradle-задачей;
- обновление не затрагивает пользовательские данные;
- образ нельзя переносить между разными ОС как универсальный архив;
- динамические зависимости нельзя принимать только по выводу `jdeps`;
- текущий немодульный launcher может выдавать предупреждение JavaFX об unnamed module.

## Отклонённые варианты

- только исполняемый JAR: оставляет установку Java и classpath пользователю;
- хранить SQLite рядом с launcher: делает обновление и права записи небезопасными;
- считать `verifyAppImage` достаточным: наличие файлов не доказывает запуск FXML/JavaFX;
- объявить Linux-образ кроссплатформенным: противоречит нативной природе `jpackage`.
