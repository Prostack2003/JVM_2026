# ADR-009: слои и порт хранилища

**Статус:** принято для практики 09.

## Контекст

В практике 08 `NutritionPlanService` одновременно выполнял сценарии, владел `ObservableList` и зависел от JavaFX. Из-за этого прикладной код был связан с конкретным способом представления данных, а замена памяти базой затрагивала бы сервис.

## Решение

- оставить инварианты в неизменяемом `NutritionPlan`;
- объявить `NutritionPlanRepository` рядом с предметными типами как порт, нужный сервису;
- внедрять порт в `NutritionPlanService` через конструктор;
- реализовать отдельный `MemoryNutritionPlanRepository`;
- хранить JavaFX `ObservableList` только в контроллере как снимок представления;
- выбирать адаптер только в `ApplicationContext`;
- обращаться к выбранной записи по устойчивому ID, а не по индексу таблицы.

## Почему интерфейс оправдан

Есть две конкретные причины замены: независимый репозиторий в тесте и будущий постоянный адаптер. Сервис проверяется без окна, а его исходник не знает, хранится ли состояние в памяти или БД. Интерфейсы для остальных классов не добавлялись, потому что там такой границы пока нет.

## Последствия

Положительные: направление зависимостей проверяемо; отказ дубликата атомарен; экземпляры памяти независимы; сортировка UI не меняет идентичность объекта. Цена решения — контроллер после операции явно обновляет свой снимок, а состав приложения требует отдельной точки сборки.
