# Объяснение решения

## Перенос в дневник КБЖУ

Счётчик используется для числа обращений к карточкам продуктов по их предметным кодам. Это сохраняет смысл повторов: код `FOOD-101` может встречаться несколько раз, если пользователь несколько раз открыл или выбрал одну карточку.

`CountMap<T>` остаётся универсальным учебным компонентом. Предметный маршрут применяет `String`, а отдельный тест с `Integer` подтверждает, что тип не зафиксирован внутри класса и не заменён `Object`.

## Выбор Map

Основной запрос звучит как «сколько обращений связано с этим кодом». Поэтому внутри используется `Map<T, Integer>`. `List` нужен, если требуется восстановить порядок каждого обращения. `Set` подходит для уникальности, но теряет кратность.

`HashMap` не задаёт порядок результата. Когда нужен стабильный вывод по коду, приложение явно создаёт `TreeMap` из снимка. Содержимое обеих карт совпадает, но только `TreeMap` гарантирует сортировку ключей. Сортировка не становится скрытым свойством счётчика.

## Почему возвращается снимок

Возврат внутренней карты позволил бы вызывающему коду записать произвольное или отрицательное количество в обход методов счётчика. Неизменяемое представление той же внутренней карты запретило бы `put`, но продолжало бы меняться вслед за счётчиком. Требование практики строже: ранее полученный результат тоже должен оставаться прежним. Поэтому `toMap` создаёт отдельную неизменяемую копию.

## Границы типов PECS

`addAll` читает ключи из источника, поэтому принимает производителя `CountMap<? extends T>`. `copyTo` записывает ключи в карту-приёмник, поэтому принимает потребителя `Map<? super T, Integer>`. В предметном примере `CountMap<String>` можно скопировать в `Map<CharSequence, Integer>`.
