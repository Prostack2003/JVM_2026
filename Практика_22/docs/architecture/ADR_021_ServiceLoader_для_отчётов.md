# ADR 021. ServiceLoader для форматов суточного отчёта

## Контекст

Практика должна показать два поставщика одного интерфейса, их присутствие в JAR и явный отказ при потере service descriptor. Предметная область дневника КБЖУ требует нескольких представлений одной сводки, но не требует выполнения неизвестного внешнего кода.

## Решение

Введён минимальный интерфейс `NutritionReportPlugin` с идентификатором и чистой операцией форматирования `DailyNutritionSummary`. Две реализации поставляются в основном JAR. Для classpath используется `META-INF/services`, для именованного модуля — `uses` и `provides`.

Штатная демонстрация запускается из собранного JAR. Отрицательная проверка создаёт отдельную копию без descriptor и требует явного ненулевого отказа.

## Альтернативы

- Условие `if` по имени формата: проще для двух вариантов, но не показывает стандартный механизм расширения.
- Reflection по строковому имени: требует ручного протокола и хуже выражает общий контракт.
- Внешний каталог JAR: отклонён, поскольку появляется новая граница доверия, которой в требованиях нет.

## Последствия

Новый формат добавляется реализацией и регистрацией без изменения клиентского цикла. Сборка обязана проверять descriptor и фактическое обнаружение. Любой поставщик получает полномочия процесса, поэтому интерфейс расширения не является защитным периметром.
