# Контракт параллельного выполнения

## Детерминированная гонка

`DeterministicCounterRace` запускает два задания. Каждое сначала читает обычный счётчик, затем оба встречаются на `CyclicBarrier` и только потом записывают `old + 1`. Оба видят `0` и оба записывают `1`: одно обновление теряется.

В том же задании `AtomicInteger.incrementAndGet()` выполняет неделимое изменение и даёт `2`. Барьер нужен для доказательства: случайный успешный запуск не доказывает отсутствия гонки.

## Пакет диагностик

1. Вход копируется через `List.copyOf` до запуска задач.
2. На каждый `NutritionPlan` создаётся один `Future<PlanDiagnostic>` в `newVirtualThreadPerTaskExecutor()`.
3. Все `Future` ожидаются с таймаутом; итоговый пакет не возвращается досрочно.
4. Результаты сохраняют порядок исходного снимка, а не порядок завершения потоков.
5. При первом отказе остальные `Future` отменяются, а причина `ExecutionException` становится `cause` прикладного исключения.
6. При прерывании ожидающего потока флаг interrupt восстанавливается.
7. `try (executor)` закрывает исполнитель; результ сообщает `executorTerminated=true`.

## Отмена

`WaitingTaskCancellation` сначала дожидается старта задачи на `CountDownLatch`, затем вызывает `cancel(true)`. Задача получает `InterruptedException`, восстанавливает флаг и выходит. После закрытия executor число активных задач равно нулю.

## Граница ресурсов

Диагностика параллелится только после чтения данных. `Connection` принадлежит SQLite-адаптеру и не передаётся в задачи. Если в будущем каждой задаче потребуется БД, нужен пул отдельных соединений с явным лимитом; количество виртуальных потоков не должно становиться лимитом базы.
